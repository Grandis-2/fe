# 페르소나별 E2E 시나리오 초안

서비스 페르소나 4명의 요구사항을 E2E 시나리오로 옮긴 초안이다. 추천 P1 8개(J1, J2, A2, H2, H3, H4, M2, M7)는 테스트로 만들었고(상태 **기존**), 나머지는 아직 초안이다. 테스트 이름이 시나리오 ID로 시작한다.

- **끝에 보여야 할 것**은 지금 코드가 하는 동작을 옮겨 적은 초안이다. 지금 동작을 그대로 정답으로 굳히지 않도록, 테스트로 만들기 전에 기대 결과를 확인한다.
- ❓는 지금 동작이 페르소나의 기대와 어긋나 보이는 곳이다. 의도한 동작인지 정한 뒤에 테스트한다.
- 상태 표기
  - **기존**: 이미 있는 테스트(`e2e/*.spec.ts`)가 다룬다.
  - **가능**: 지금 코드로 바로 만들 수 있다.
  - **목 수정**: 목 서버에 스위치를 더해야 만들 수 있다.
  - **없음**: 기능 자체가 없어 테스트할 수 없다.

## 이미 자동화된 테스트

| 파일                       | 다루는 것                                                                                                      |
| -------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `login.spec.ts`            | 첫 가입 후 원래 화면으로 복귀(버그로 `test.fail`), 가입한 회원 재로그인, 새로고침 후 로그인 유지               |
| `cart-payment.spec.ts`     | 장바구니 합계, 결제 페이지 검증, 결제창에 넘긴 금액, 상품 상세 바로 구매, 승인 성공·재진입·금액 위조·서버 장애 |
| `preorder.spec.ts`         | 비회원 차단, 대기열을 거쳐 접수, 이미 예약한 모델 재접수                                                       |
| `server-error.spec.ts`     | 홈·상품 상세 서버 장애 화면                                                                                    |
| `preorder-open.spec.ts`    | J1 오픈 시각에 새로고침 없이 버튼이 열림                                                                       |
| `preorder-mobile.spec.ts`  | J2 휴대폰에서 하단 탭부터 접수까지                                                                             |
| `preorder-payment.spec.ts` | A2 결제 실패 뒤 같은 순번으로 다시 결제                                                                        |
| `preorder-retry.spec.ts`   | H2 동시 두 번 클릭, H3 일시 장애 뒤 재시도, H4 응답 유실 뒤 재전송                                             |
| `admin.spec.ts`            | M2 외부 등록 실패 사유 조회, M7 회원 주문을 관리자가 배송 완료 처리                                            |

## 1. 이진우: 0초 폰켓팅 유저

> "오픈 땡 하자마자 실패 없이 신청하고, 내 예약 상태가 어떻게 진행되는지 실시간으로 확인하고 싶어요."

모바일로 D-Day 카운트다운에 맞춰 신청하고, 마이페이지에서 예약 상태를 자주 확인한다.

| ID  | 상태 | 시나리오                                                                                                    | 끝에 보여야 할 것                                                                                                                                                         |
| --- | ---- | ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| J1  | 기존 | 시계를 08:59:50(한국 시간)으로 두고 사전예약 상세에 들어가 10초 기다린다                                    | 처음엔 "사전예약 하러가기"가 비활성이고 "1분 후 시작"과 카운트다운이 보인다. 09:00이 되면 새로고침 없이 버튼이 활성으로 바뀐다                                            |
| J2  | 기존 | 휴대폰 화면 크기로 하단 탭 "사전예약" → 상세 → 모델 시트 → 대기열 → 하단 고정바 "사전예약하기"까지 진행한다 | 결제 페이지(`/payment?preorderId=…`)에 도착한다                                                                                                                           |
| J3  | 가능 | 맥북 프로 14 상세에서 색상과 용량을 바꿔 본다                                                               | 512GB를 고르면 2,151,000원이 2,268,000원으로 바뀐다. 색상은 가격을 바꾸지 않는다                                                                                          |
| J4  | 가능 | 접수 직후 사전예약 내역을 보고, 5초 뒤 다시 본다                                                            | "접수 완료"에서 "구매 확정 대기"로 바뀌고 "예약 순번 1,287번"이 보인다 ❓ 내역이 자동으로 갱신되지 않아 다시 들어가야 바뀐 상태가 보인다(페르소나는 실시간 확인을 원한다) |
| J5  | 가능 | 사전예약 내역에서 "예약 취소" → 확인 모달 → "예약 취소"                                                     | "예약 취소를 요청했어요." 토스트 뒤 "취소 처리 중"이 된다. "취소 완료"는 다시 들어가야 보인다 ❓ 자동 갱신이 없다                                                         |
| J6  | 가능 | 헤더 종 아이콘 → "사전예약 등록 완료" 알림을 누른다                                                         | 사전예약 내역(`/mypage?state=preorder-check`)으로 이동한다                                                                                                                |
| J7  | 가능 | 오픈 예정 사전예약에서 모델별 종 아이콘을 켠다                                                              | CTA가 "알림 신청 완료 · N개 모델"로 바뀐다                                                                                                                                |
| J8  | 없음 | 예약 시작·배송 시작 알림을 받는다                                                                           | 목 알림은 고정된 4개뿐이고, 예약 진행에 따라 새 알림이 생기지 않는다                                                                                                      |
| J9  | 없음 | 예약 상세 화면에서 진행 상태를 본다                                                                         | 회원용 예약 상세 화면이 없다. 사전예약 내역 카드가 전부다                                                                                                                 |

## 2. 김아영: 혜택 및 결제 민감 유저

> "예약 과정에서 한순간의 오류로 결제가 실패해서 내 차례가 날아갈까 봐 불안해요."

혜택을 꼼꼼히 확인하고, 결제 실패로 예약이 취소되는 것을 가장 두려워한다. 마음이 바뀌면 바로 취소하고 싶어 한다.

| ID  | 상태 | 시나리오                                                          | 끝에 보여야 할 것                                                                                                                      |
| --- | ---- | ----------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| A1  | 기존 | 장바구니 결제 승인이 실패한다                                     | `cart-payment.spec.ts`가 금액 위조와 승인 서버 장애를 다룬다                                                                           |
| A2  | 기존 | 사전예약 결제가 실패한다 → "다시 결제하기" → 다시 결제해 성공한다 | "사전예약 구매가 완료되었어요"가 뜬다. 예약 순번은 처음 받은 1,287번 그대로다(실패해도 차례가 날아가지 않는다)                         |
| A3  | 가능 | 결제 실패 직후 사전예약 내역을 본다                               | 예약이 남아 있고 "구매 확정 마감까지"가 보인다 ❓ 태그가 "구매 확정 대기"가 아니라 "결제 진행 중"이다. 실패했는데 진행 중이라고 보인다 |
| A4  | 가능 | 사전예약 결제창에서 취소하고 돌아온다                             | 실패 화면이 아니라 결제 페이지로 돌아간다(장바구니 주문과 반대 동작)                                                                   |
| A5  | 가능 | 결제를 마친 "예약 확정" 상태에서 예약을 취소한다                  | 취소된다 ❓ 목이 환불을 흉내 내지 않아 주문은 "결제 완료"로 남는다                                                                     |
| A6  | 가능 | 결제 기한(24시간)이 지난다                                        | "결제 기한 지남" 태그가 붙고, 결제 페이지에 "결제 기한이 지나 결제할 수 없어요."가 뜨며 결제 버튼이 막힌다 ❓ 자동 취소는 되지 않는다  |
| A7  | 가능 | 상품 상세의 사전예약 혜택과 결제 페이지 금액을 비교한다           | "사전예약 혜택 (10%)" -239,000원이 적용된 금액이 두 화면에서 같다                                                                      |
| A8  | 없음 | 알림 수신 설정을 켜고 끈다                                        | 마이페이지에 알림 설정이 없다. 있는 건 모델별 오픈 알림 토글뿐이다                                                                     |
| A9  | 없음 | 결제 실패 알림을 받는다                                           | 결제 실패 알림이 없다                                                                                                                  |

## 3. 박성민: 운영 & 트래픽 관리자

> "대규모 사용자가 한 번에 몰려도 시스템 장애 없이 예약부터 배송까지 안정적으로 처리되어야 합니다."

재고와 예약 상태를 실시간으로 지켜보고, 부하가 걸리면 지연시간을 조정하거나 실패 사유를 조회해 대응한다.

| ID  | 상태 | 시나리오                                                                       | 끝에 보여야 할 것                                                                                           |
| --- | ---- | ------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------- |
| M1  | 가능 | 관리자 로그인 / 일반 회원이 `/admin`에 들어감 / `locked` 계정으로 로그인       | 관리자 홈으로 간다 / "관리자 계정으로 로그인해 주세요."가 뜬다 / 버튼이 "5초 후 다시 시도"로 막힌다         |
| M2  | 기존 | 예약 현황에서 실패 사유 찾기: 상태 카드 → "외부 등록 실패" 탭 → RSV-93355 상세 | 외부 등록 실패가 3건이고, 상세의 "외부 연동 기록"에 "HTTP_503 — Service Unavailable"과 시도 3회가 보인다    |
| M3  | 가능 | 실패한 예약을 재처리한다                                                       | 그 예약이 "확정 / 결제 대기"로 바뀌고 외부 등록 실패 카드가 2건이 된다                                      |
| M4  | 가능 | 일반 상품의 재고를 조회하고, 결제 대기보다 적게 재고를 줄여 본다               | 전체·결제 대기·남은 수량이 보인다. 줄이면 "이미 확보·판매된 수량보다 적게 줄일 수 없습니다."가 뜬다         |
| M5  | 가능 | 사전예약 상품 등록: 오픈을 30분 안으로 잡는다 / 제대로 등록한다                | "오픈은 지금부터 30분 뒤 이후여야 합니다." / 등록되면 상품 목록 맨 위에 보인다                              |
| M6  | 가능 | Mock 설정에서 일시 실패 확률을 올리고 부하 검증 "시험 시작"                    | 외부 등록 실패가 늘고 "외부 등록 실패가 시험 시작 뒤 N건 늘었습니다…" 판정이 뜬다(1분쯤 걸리는 느린 테스트) |
| M7  | 기존 | 회원이 결제한 주문을 관리자가 주문 상세에서 배송 완료까지 처리한다             | 회원의 주문 내역 상태가 같이 바뀐다. 회원 화면과 관리자 화면이 목에서 실제로 이어진 유일한 곳이다           |
| M8  | 가능 | 관리자가 예약을 취소한다: 사유 5자 미만 / 정상                                 | 사유가 5자 미만이면 막힌다 / 정상이면 "예약 취소를 요청했습니다."                                           |
| M9  | 가능 | 사전예약(홍보)을 등록하고 수정한다                                             | 필수 칸이 정해진 순서대로 검증되고, 등록하면 목록에 생긴다. 삭제 기능은 없다                                |
| M10 | 없음 | 시스템 장애 알림을 받고, 사용자 대상 예약 진행 알림을 보낸다                   | 관리자 종 아이콘은 눌러도 아무 일이 없고, 관리자 알림 화면은 "준비 중"이다                                  |

❓ 관리자 목 데이터와 회원 목 데이터가 따로 있다. 그래서 "회원이 예약 → 관리자가 예약 현황에서 확인" 같은 시나리오는 지금 만들 수 없다(주문만 이어져 있다).

## 4. 최하늘: 불안정 환경 재도전 유저

> "신청 버튼 눌렀는데 화면이 멈춰서 다시 눌렀어요. 혹시 두 번 접수된 거 아니겠죠?"

지하철 등 불안정한 네트워크에서 접속하고, 응답이 늦으면 다시 누르거나 새로고침한다.

| ID  | 상태    | 시나리오                                                                       | 끝에 보여야 할 것                                                                                                                                 |
| --- | ------- | ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| H1  | 가능    | 상품 페이지에서 "사전예약하기"를 누른 직후                                     | 등록을 기다리는 약 5초 동안 버튼이 비활성이다                                                                                                     |
| H2  | 기존    | 같은 순간에 두 번 클릭한다                                                     | 요청이 두 번 나가도 예약번호는 같다. 내역에 1건, 순번 1,287번만 있고 1,288번은 없다                                                               |
| H3  | 기존    | 서버 일시 장애 중에 누르고, 장애가 풀린 뒤 다시 누른다                         | 처음엔 "서버에 일시적인 문제가 발생했습니다…" 토스트가 뜬다. 다시 누르면 같은 멱등키로 접수되고 예약은 1건만 생긴다                               |
| H4  | 기존    | 서버엔 접수됐는데 응답만 잃어버린 상황에서 다시 누른다                         | 최초 접수 응답이 재생되어 같은 예약번호로 결제 페이지에 간다                                                                                      |
| H5  | 가능    | 같은 멱등키로 옵션만 바꿔 다시 보낸다(422)                                     | "이미 접수한 예약이 있어요. 사전예약 내역에서 확인해 주세요." 토스트 뒤 사전예약 내역으로 간다 ❓ 422("내용이 다름")인데 문구는 "이미 접수함"이다 |
| H6  | 가능    | 접수 중에 새로고침한다                                                         | 사전예약 내역에 순번 1,287번이 남아 있다. 다시 누르면 "사전예약 페이지에서 대기열을 거쳐야 예약할 수 있어요."가 뜬다                              |
| H7  | 가능    | 서버 재기동을 흉내 낸다(새로고침으로 목 메모리 초기화) → 같은 키로 다시 보낸다 | 예약은 남아 있다. 재전송은 "대기열에 다시 입장해 주세요."로 막히고, 다시 줄 서서 접수하면 "이미 접수한 예약"이 떠 중복이 생기지 않는다            |
| H8  | 가능    | 예약번호가 든 주소(`/payment?preorderId=…`)를 새로고침하거나 새 탭에서 연다    | 같은 예약이 다시 조회된다 ❓ 결과 화면(`/result?status=preorder`)은 새 탭에서 열면 예약 정보가 비어 있다                                          |
| H9  | 목 수정 | 아직 처리 중인 키로 다시 요청한다(409)                                         | 목이 요청을 바로 끝내서 "처리 중" 상태가 없다                                                                                                     |
| H10 | 목 수정 | 응답이 느린 동안 여러 번 누른다                                                | 접수 응답을 늦출 스위치가 없다. H9와 같은 목 수정으로 같이 해결된다                                                                               |

"외부 등록이 두 번 되지 않음"은 화면에서 내역 1건·순번 하나로만 확인할 수 있다. 등록 이력을 보여 주는 회원 화면이 없다.

## 정할 것

1. **❓ 9곳이 의도한 동작인지.** 특히 J4·J5(내역 자동 갱신 없음), A3("결제 진행 중" 태그)는 페르소나가 바로 겪는 부분이다.
2. **기능이 없는 6개를 어떻게 할지.** J8, J9, A8, A9, M10, 회원↔관리자 예약 연결. 테스트에서 뺄지, 기능을 만들 일로 따로 둘지 정한다.
3. **목 수정(H9, H10)을 할지.** 목에 "접수 지연" 스위치를 하나 더하면 둘 다 만들 수 있다.

## 테스트 작성 메모

- **도우미**: 로그인·결제·대기열·관리자 로그인 도우미는 `e2e/fixtures.ts`에 있다(`loginAs`, `loginAsAdmin`, `passPreorderQueue`, `fillPaymentForm`, `stubTossPayments`의 `failFirst` 등).
- **동시 실행**: `workers: 2`. 브라우저 4개가 개발 서버 하나에 붙으면 CPU가 차서 결제 승인·대기열이 시간 안에 안 끝난다. 대기열을 거치는 테스트는 제한 시간을 90초로 둔다.
- **시계**: 사전예약은 한국 시간 09:00에 연다. `setKstClock`으로 시각을 정한다. 특정 순간을 보려면 화면을 불러온 뒤 `page.clock.pauseAt` → `runFor`로 흘린다(J1). `setFixedTime`은 목 대기열을 멈추게 하니 쓰지 않는다.
- **목 장애**: sessionStorage `mock-fault`를 `all`/`queue`/`confirm`으로 두면 해당 요청이 503으로 실패한다(`setMockFault`). 사전예약 접수만 실패시키는 값은 없다.
- **목 상태 수명**: 회원 주문·예약·장바구니는 localStorage `nova-order-mock-db-v2`, 인증은 `nova-auth-mock-db`에 남는다. 대기열·입장권, 관리자 화면의 목 데이터는 메모리에만 있어 `page.goto`/새로고침이면 초기화된다. 관리자 테스트는 바꾼 뒤 사이드바로 이동한다.
- **모바일**: 파일 단위로 `test.use({ viewport, isMobile, hasTouch })`를 둔다(`preorder-mobile.spec.ts`). 상품 상세는 799px 이하에서 하단 고정바만 보인다.
- **요청 확인**: MSW가 응답하는 요청은 `page.route`로 가로챌 수 없다. 요청 횟수·멱등키 확인은 `page.on('request')`로 본다(`collectPreorderSubmits`).
- **관리자 로그인**: `admin` / `admin1234`. 관리자로 로그인하면 회원 로그인은 풀린다.
